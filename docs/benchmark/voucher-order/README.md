# tb_voucher_order 性能测试数据准备

本目录只负责准备独立的 `hmdp_benchmark` 数据库，不包含索引优化，也不修改 Java 代码。

## 数据设计

- 从 `hmdp` 复制 `tb_user`、`tb_shop`、`tb_voucher` 的真实基础数据。
- 从真实且商铺关联有效的券中循环取模板，在测试库生成 3000 个历史秒杀活动批次。
- 选取真实用户中 ID 最小的 1000 人：
  - 10 个高频用户，每人 3000 单，共 30000 单；
  - 90 个中频用户，每人 300 单，共 27000 单；
  - 700 个普通用户，每人 48 单，共 33600 单；
  - 200 个普通用户，每人 47 单，共 9400 单。
- 总订单数精确为 100000；同一用户不会对同一券批次生成第二笔订单。
- 状态比例为：未支付 15%、已支付 35%、已核销 20%、已取消 20%、退款中 3%、已退款 7%。
- 下单时间覆盖最近 180 天：约 50% 在最近 30 天、30% 在 31～90 天、20% 在 91～180 天。
- 未支付订单中约 20% 在最近 5 分钟内，其余为超时未支付，用于超时扫描实验。
- 已支付、核销及退款订单的 `pay_time`、`use_time`、`refund_time` 均晚于下单时间并符合状态语义。

之所以需要生成历史券批次，是因为当前券数量无法同时满足“10 万订单”“1000 个用户的高/中/低频分层”和“一人一券”。这些批次只存在于 `hmdp_benchmark`，其字段来源于真实券，且 `shop_id` 始终关联已复制的真实商铺。

## 执行顺序

在 MySQL 8.0 客户端中依次执行：

1. `01_create_benchmark_schema.sql`
2. `02_generate_orders.sql`
3. `03_validate_data.sql`

示例（请自行填写连接参数，不要把密码写入仓库）：

```bash
mysql -h 127.0.0.1 -P 3307 -u root -p < 01_create_benchmark_schema.sql
mysql -h 127.0.0.1 -P 3307 -u root -p < 02_generate_orders.sql
mysql -h 127.0.0.1 -P 3307 -u root -p < 03_validate_data.sql
```

## 安全说明

- `01` 会重建且仅重建 `hmdp_benchmark` 中列出的四张表；不会删除或更新 `hmdp` 数据。
- `02` 包含数据库名保护检查，当前库不是 `hmdp_benchmark` 时会主动报错。
- `02` 可重复执行：它只清理自身 ID 区间内的测试订单和带指定标记的测试券批次。
- 本阶段没有为 `tb_voucher_order` 创建任何二级索引；表上仅保留主键。
- 执行前建议再次确认 `SELECT DATABASE()` 和源库名称。
